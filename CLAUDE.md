# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ironland-compositor` is a Wayland compositor built on [Smithay](https://github.com/Smithay/smithay) (git dependency, pinned by rev in `Cargo.toml`), originally derived from Smithay's `anvil` example (`AnvilState` in `src/state/mod.rs`). It's designed to pair with a companion shell called molunga-shell (built on Quickshell), and ships two small companion binaries plus a Go settings GUI alongside the compositor itself.

The repo is developed inside a Nix flake / direnv environment (`.envrc` runs `use flake` and adds `scripts/` to `PATH`).

## Commands

Enter the dev shell first (direnv does this automatically via `.envrc`; otherwise `nix develop`).

- `run` — build and run the compositor (`cargo run`, nested via winit by default: `run --winit`). Defined in `scripts/run`.
- `run-vm` — boots a full NixOS VM (via `nix build .#nixosConfigurations.compositor-vm...`) with the compositor autostarting on login as user `dev`; use this to test standalone/tty-udev behavior or session integration that a nested winit window can't exercise. See `scripts/run-vm` for host GL caveats.
- `build-vm-guest <entry id> <nixpkgs package>...` — builds one program's NixOS guest disk image (`nix/vm-guest.nix`: sshd + waypipe + just those packages) used by "launch in VM" and prints the `[vm.programs]` config section pointing at it; creates a dedicated ssh key on first run.
- `help` — lists the scripts above.
- `cargo build` / `cargo run -- --winit` / `cargo run -- --tty-udev` — standard cargo entry points; `--winit` nests the compositor in an existing session (development), `--tty-udev` runs standalone on a tty via DRM/KMS + libinput.
- `cargo test` — unit tests live inline (`#[cfg(test)]`) in `src/config.rs`, `src/wallpaper.rs`, `src/ui/launcher.rs`, `src/shell/workspace.rs`, `src/shell/vm.rs`, `src/shell/vm_state.rs`, `src/shell/vm_gateway.rs`, `src/shell/vm_tor.rs`, `src/ui/vm_overview.rs`, `src/render/vm_badge.rs`. Run a single test with `cargo test <name>`.
- `cargo clippy` / `cargo fmt` — both `clippy` and `rustfmt` are provided by `devShells.default` in `flake.nix`.
- `nix build .#default` — builds the compositor via crane (`packages.default` in `flake.nix`); `nix build .#settings-gui` builds the Go GUI.

### `gui-settings/` (separate Go module)

A standalone Fyne GUI for editing the compositor's TOML config (`ironland-compositor/gui-settings` module, Go 1.26). It has its own devshell: `nix develop .#settings-gui` (sets `GOFLAGS=-tags=wayland`, required for Fyne's native-Wayland glfw backend — don't drop that tag when invoking `go build`/`go test` outside the devshell). From within `gui-settings/`: `go test ./...`, `go test -run TestName ./...`. Note `gui-settings` (the built binary name) is gitignored — don't confuse it with the source directory of the same name.

There is no CI config in this repo (no `.github/workflows`); the closest thing is `nix flake check`-style building via the flake outputs above.

## Architecture

### Crate layout

`src/` is grouped into `backend/`, `input/`, `protocols/`, `render/`, `ui/` and `shell/`. `lib.rs` re-exports the leaf modules at the crate root, so `crate::foo::` paths (e.g. `crate::wallpaper`) still resolve. The three largest files are split into submodule directories sharing the parent's imports via `use super::*`: `state/` (`handlers.rs` = Smithay handler trait impls, `config.rs`, `repaint.rs`), `backend/udev/` (`device.rs` = DRM device/connector lifecycle, `render.rs`), `input/input_handler/` (`keyboard`, `pointer`, `touch`, `tablet_tool`, `gestures`, `actions`, `windowed`).

- `src/main.rs` — parses `--winit`/`--tty-udev` and dispatches to `winit::run_winit()` / `udev::run_udev()`.
- `src/state/mod.rs` — `AnvilState<BackendData>`, the central compositor state struct and the hub that Smithay's handler traits (`CompositorHandler`, `SeatHandler`, etc.) are implemented on. Almost every subsystem module is reached through fields/methods on this type.
- `src/backend/winit.rs` / `src/backend/udev.rs` — the two backends selectable at runtime, plus `src/backend/x11.rs` (feature-gated) for an X11 backend. `winit` nests in an existing session for development; `udev` runs standalone using DRM/KMS + libinput and needs `backend/session.rs`.
- `src/shell/` — window management: `xdg.rs` (native Wayland toplevels/popups), `x11.rs` (XWayland client handling — X11 windows tile the same as native toplevels via `tiling::should_tile_x11`; dialogs/utility/fixed-size windows opt out and stay floating), `tiling.rs` (automatic BSP/"dwindle" layout, Hyprland-style, one tree per output), `workspace.rs` (virtual desktops layered on top of tiling; per-output, with `PerMonitor` vs `Combined` switching modes and optional dynamic growth), `grabs.rs`/`ssd.rs`/`element.rs` (move/resize grabs, server-side decorations, the generic window element type).
- `src/shell/vm.rs` — programs started "as virtual": **one program per VM**: only desktop entries with an image in `vm.programs` (entry id -> qcow2; plus `/etc/ironland-compositor/vm/<entry id>.qcow2`, merged by `VmSettings::all_programs`/`image_for`) can be launched, each from the image that has just that program installed (otherwise `VmError::NotConfigured`). Each launch boots its own headless QEMU VM (`-snapshot` of that image, guest port 22 forwarded to a free loopback port), then runs `waypipe ssh` against it so the guest app's windows become ordinary `xdg_toplevel`s here. Every VM gets a **private Wayland listening socket**; clients accepted on it are tagged `ClientState::vm`, which is how `WindowElement::vm_id()` knows a window is virtual (not pid or app-id guessing). A probe thread waits for the guest's SSH banner and reports over a calloop channel; all child processes are spawned from the main thread with `PR_SET_PDEATHSIG` (that signal is per-*thread*, so don't spawn from helpers). `waypipe` hangs rather than exits when its ssh fails, so a startup deadline (`vm.startup_timeout_secs`) with no connected client is what detects a dead VM. A 1 Hz reaper timer exists only while VMs do. **Persistent** launches (launcher's right tab, `launch_in_vm(.., true)`) run on a per-app qcow2 overlay (`src/shell/vm_state.rs`); when the program exits cleanly the reaper calls `begin_save`, a helper thread issues QMP `savevm` + `quit`, and QEMU *exiting 0* during the saving phase is the success signal (`find_finished`); the next launch starts QEMU with `-loadvm` and a guest-agent `guest-set-time` (a restored clock is stale — measured 30 s behind after 25 s). The machine definition must be identical between save and restore (`machine_fingerprint`; QEMU exits if not, handled as `RestoreFailed` -> cold boot). A replaced base image moves the whole state dir aside as `*.stale-<time>` rather than deleting user data. Live tests: `IRONLAND_TEST_VM_IMAGE=... IRONLAND_TEST_VM_KEY=... cargo test --lib live_ -- --ignored --nocapture`. **Guest login key**: not baked into the image. `launch_in_vm` collects public keys (`authorized_keys`: `vm.public_key`/`public_key_file`, else `<ssh_key>.pub`, else `~/.ssh/id_ed25519.pub` + `ssh-add -L`) and appends them to `extra_qemu_args` as an SMBIOS OEM-string systemd credential (`ironland.authorized_keys`, base64); the guest's sshd reads `/run/credentials/@system/` through `AuthorizedKeysCommand` (`nix/vm-guest.nix`). Being an extra arg puts the keys in `machine_fingerprint`, so a changed key cold-boots a persistent VM instead of restoring one that still has the old key. With `ssh_key` unset ssh authenticates through the agent. `services.ironland-compositor.vm.programs.<entry id>.packages` (`nix/module.nix`; `vm.enable` is on by default, `compositor-vm` turns it off) builds one guest image per program with the system and links it at `/etc/ironland-compositor/vm/<entry id>.qcow2`, which `VmSettings::all_programs` merges with `[vm.programs]` (needed because a user's config.toml replaces `/etc`'s wholesale). Each image is ~2.7 GB (the guest's base NixOS), so every program costs that much store space. The compositor polls the programs (`announce_vm_programs`, with the config reload check) so images appearing after a NixOS switch reach the shell without a restart. A host desktop entry must exist for each program: the compositor resolves the `Exec` there. The guest `Exec` is passed to ssh as **one pre-quoted string** (`remote_command`) because ssh re-parses its args with the guest shell.
- `src/ui/vm_overview.rs` — the VM overview overlay (`toggle_vm_overview`, `super+o` by default). Keys while open: Up/Down select, **O/T/X** put the selected VM into online/Tor/offline mode, N/Enter/Space flip online<->offline (Tor -> offline), **I** new Tor identity, Esc/Q or the shortcut again close. The pointer works too (the overlay grabs it, `surface_under` reports nothing while it is open): a click on a VM's rows selects it, on a button does it, outside the panel closes (`AnvilState::vm_overview_click`, `VmOverviewState::hit_test`). Lists running VMs (persistent or throw-away, phase, uptime, CPU % of one core and QEMU's resident memory against the guest RAM, and the route their traffic takes), the persistent VMs' state directories with their on-disk footprint (`vm_state::list_persisted`, allocated blocks so sparse overlays count honestly; includes `*.stale-*` dirs) and the mode each starts in, and every program that has a VM image. Pure data model + `layout()` (unit-tested) + rasterizer in the launcher's style; the data is gathered by `AnvilState::refresh_vm_overview` in `shell/vm.rs`, which a 1 Hz calloop timer re-runs only while the overlay is visible.
- **VM network modes** (`vm_state::NetMode`: online / tor / offline; `AnvilState::set_vm_network`). Every VM has *three* virtio NICs (`qemu_args`), in the order the guest prefers them for its default route (dhcp metrics 1000 + ifindex: the earlier NIC wins): `inet` (QEMU NAT onto the host, 10.0.2.0/24), `tor` (a `-netdev stream` unix socket served by the VM's own gateway, 10.0.4.0/24) and `mgmt` (`restrict=on`, 10.0.3.0/24, carries the ssh `hostfwd` that `waypipe` runs over, so the compositor's way in works in every mode - a link-down on a NIC drops all traffic through it, including an ssh session, hence a separate card). A mode is nothing but which links are up, set with QMP `set_link name=inet|tor` (`vm_state::set_network_over_socket`; what is taken away is changed first; on a `vm-net-<id>` helper thread -> `VmEvent::NetworkSet`, which carries the QEMU pid so a result from a replaced QEMU is ignored). The Tor card is also up while online (it only leads into Tor); offline sets both down. Every VM has a QMP socket (QMP serves one client at a time, so helpers connect, send and hang up). **Persistence**: `PersistMeta.network` in `meta.json` (`MetaFile` also reads the earlier `network_enabled` bool: `false` -> offline, never fails open), written on each successful switch and kept in `PersistState.meta` so the save at the end of the run doesn't overwrite it. A VM whose metadata says tor/offline starts with `-S` and its links are set before `cont` (`held`), so the guest never runs in the wrong mode; if that fails the VM is ended (`EndReason::NetworkFailed`) rather than let loose. The NIC layout is part of `machine_fingerprint` (`net=3`), so states saved before it cold-boot once instead of failing to load. Only *running* VMs can be switched. Guest cooperation: "earlier NIC wins the default route" holds for dhcpcd/networkd defaults and `nix/vm-guest.nix`; an image giving the NICs equal metrics could route internet traffic out of the wrong one.
- `src/shell/vm_gateway.rs` — the **transparent Tor gateway**, one thread per VM (`Gateway::spawn`, which must run before QEMU starts: QEMU connects to the unix socket at startup). A userspace stack (smoltcp, `any_ip`) on the other end of the `tor` NIC, frames length-prefixed (4 bytes BE). It serves: DHCP (hand-built replies via `smoltcp::wire`; the guest gets 10.0.4.15, router and DNS 10.0.4.2), DNS over UDP to *any* address (every A query gets a made-up address from 10.192.0.0/10 and the name is remembered, so a connection to it is handed to Tor **by name**: the exit resolves it, no DNS leaves the host, `.onion` works; AAAA/other types get empty answers), and TCP to any address (terminated here, relayed over SOCKS5 to the host Tor: by name for made-up addresses, by IP otherwise; private/loopback/link-local/multicast/unassigned-fake destinations and everything while Tor is down are **refused at the SYN with a hand-built RST** - accepting first and resetting later looks like a success to the guest for a moment). Everything else (other UDP, ICMP, ARP for anything but 10.0.4.2) is dropped before the stack sees it - important: `any_ip` makes smoltcp answer ARP for *every* address, which made the guest's DHCP duplicate-address probe see a conflict and DECLINE its lease. SOCKS handshakes are non-blocking state machines in the same single thread (`rustix::event::poll` on the guest socket and every Tor socket). Each VM logs in to Tor with username `ironland-vm<id>` and password `identity-<n>`; `IsolateSOCKSAuth` turns that into separate circuits per VM and per identity. `Gateway::new_identity` (the overlay's button) bumps `n` and the loop resets every open guest connection within ~20 ms, so nothing before stays linked to what follows. The gateway has no other way out, so Tor mode cannot leak by construction; whether the card is connected at all is the QMP link state.
- `src/shell/vm_tor.rs` — `TorService`: the host's own `tor` (`vm.tor_binary`, default `tor`, on the compositor's PATH - `flake.nix` suffixes it), started by the compositor (main thread, `PR_SET_PDEATHSIG`) when a VM first goes into Tor mode and stopped when none uses it (`AnvilState::tor_tick`, run by the 1 Hz reaper, on mode changes and in `end_vm`; it also restarts a Tor that died, at most every 5 s). SOCKS-only on a free loopback port (`SocksPort 127.0.0.1:<p> IsolateSOCKSAuth`, no ControlPort/TransPort), data dir `$XDG_DATA_HOME/ironland-compositor/vm/tor` (keeps the consensus: re-bootstrap takes seconds). Bootstrap progress and the last complaint are read from its output for the overlay. The port is shared with the gateways through `TorEndpoint` (0 = not running -> they refuse).
- Live tests (need `/dev/kvm`, a guest image from `scripts/build-vm-guest`/the NixOS module and `qemu`): `IRONLAND_TEST_VM_IMAGE=... IRONLAND_TEST_VM_KEY=... cargo test --lib live_ -- --ignored --nocapture --test-threads=1`. `live_network_modes_online_tor_offline` (all three modes against a fake SOCKS "Tor" that records what it is asked for), `live_persistent_vm_in_tor_mode_restores_in_tor_mode`, `live_real_tor_end_to_end` (real `tor` + internet: a clearnet name and a v3 .onion through guest -> gateway -> Tor, before and after a new identity). From the dev shell `LD_LIBRARY_PATH` breaks QEMU (a glibc mismatch with alsa-lib): put a wrapper that unsets it first on PATH.
- `src/render/vm_badge.rs` — the cube-on-blue-tile badge drawn in a virtual window's top-right corner (added in `WindowElement::render_elements`); rasterized in code, no asset.
- `src/config.rs` — user settings (keyboard layout + shortcuts) loaded from a TOML file, checked in this priority order: `$IRONLAND_COMPOSITOR_CONFIG` → `$XDG_CONFIG_HOME/ironland-compositor/config.toml` → `/etc/ironland-compositor/config.toml` (written by the NixOS module) → hardcoded defaults. A malformed file is logged and ignored, not fatal.
- `src/input/input_handler.rs` — keyboard/pointer input dispatch; the single call site that resolves key bindings to actions and routes surface-targeted grabs to `focus_grab.rs`/`shortcuts.rs`.
- `src/render/` (`mod.rs` is the pipeline; also `drawing.rs`, `font.rs`, `cursor.rs`, `wallpaper.rs`) — rendering pipeline, including a tiny embedded 5x7 bitmap font for the launcher overlay (no font-rendering dependency) and per-output wallpaper scaling/caching.
- `src/ui/launcher.rs` — XDG desktop entry discovery and fuzzy filtering for the app launcher overlay. The overlay (`LauncherState` in `render/drawing.rs`) has three tabs, switched with **Left**/**Right** (`KeyAction::LauncherTabLeft`/`Right`, stopping at the ends): `Vm` (left) | `Apps` (middle, the default) | `Persistent` (right). The VM tabs list only entries that have a VM program (`set_vm_programs`, called when opening) and exist only when there is one; Enter launches according to the tab: on the host from `Apps`, else via `AnvilState::launch_selected_in_vm(persistent)`, which keeps the launcher open with the reason in its footer if that fails. The bottom lines (`footer_lines`) show the key hints for the current tab.
- `src/ui/lock.rs` — screen lock (`lock_screen` action, `super+l` by default). While `AnvilState::lock` is locked, `keyboard_key_to_action` routes keys to the password field, the input handlers drop clicks/touch/gestures, and both backends render only the cursor + lock panel (`render::output_elements(.., locked)`). The password is checked on a worker thread through a minimal libpam binding (service `ironland-compositor`, registered by `nix/module.nix`); the result returns via a calloop channel to `finish_unlock_attempt`.
- `src/backend/session.rs` — announces the compositor session to systemd/D-Bus (`graphical-session.target`), required for `xdg-desktop-portal` and portal-backed dialogs to start at all. `announce_session_start` is deferred until XWayland has settled (so `DISPLAY` is exported first), and, if `session.start_shell` is set, ends by running `systemctl --user --no-block start <session.shell_unit>` — the one safe place to start the shell, since a unit started earlier is forked without `DISPLAY` and never sees the later update. `--no-block` matters: the shell is a client of this compositor, so waiting on it would deadlock. `ironlandctl session units` lists candidate units for the GUI/shell pickers.

### Custom Wayland protocol extensions (`protocols/*.xml`, `src/protocols/ironland_protocols.rs`)

Several protocols are custom to this compositor, generated at compile time via `wayland-scanner` (see `src/protocols/ironland_protocols.rs` module doc for why these aren't reused from `hyprland-*` equivalents — this compositor's needs are narrower):

- `ironland-shortcuts-v1` (`src/protocols/shortcuts.rs`) — named keybinding actions exposed to clients; `fire()` is the single entry point, called from `input_handler.rs`. Also backs the `GlobalShortcuts` xdg-desktop-portal backend.
- `ironland-focus-grab-v1` (`src/protocols/focus_grab.rs`) — single-surface pointer/key focus grabs (e.g. Quickshell popups); `check()` is the single entry point.
- `ironland-workspace-windows-v1` (`src/protocols/workspace_windows.rs`) — per-window workspace membership; `sync()` is the single entry point, called alongside `foreign_toplevel::sync` and `ext_workspace::ext_workspace_sync` on the same event set (window map/unmap, title/app-id change, workspace move).
- `ironland-vm-launch-v1` (`src/protocols/vm_launch.rs`) — lets the shell's launcher start an installed app in a VM (`launch(entry, mode)`, mode = throwaway | persistent; see `src/shell/vm.rs`; version 2 adds `program`/`programs_done` events listing the entry ids that have a VM, resent as a complete list whenever it changes - `VmLaunchState::update_programs`). The client names a **desktop entry id**, never a command: the compositor resolves it with `launcher::find_entry` and runs that entry's own `Exec` in the guest, so the protocol can't run arbitrary commands. Each request makes an `ironland_vm_launch_v1` object that becomes a `vm_launch::Watcher` held by the VM (`starting`/`running`/`saving`/`finished`, or just `failed`); the VM never depends on it. The manager also sends `availability(configured)` (any program) on bind and when the program set changes. The global is hidden (`can_view`) from VM guests (`ClientState::vm`) and security-context clients. Has real wire tests (a `wayland-client` against the server over a socketpair) in `vm_launch::wire_tests`; the shell keeps its own copy of the XML in `plugin/protocols/`.
- `ironland-display-filter-v1` (`src/protocols/display_filter.rs`, rendered by `src/render/tint.rs`) — a client sets a color temperature in kelvin and the compositor draws a warm translucent overlay over every output (night mode); the filter lives only as long as the requesting protocol object. Scheduling is the client's job.
- `ironland-cinema-mode-v1` (`src/protocols/cinema_mode.rs`, rendered by `src/render/cinema.rs`) — "cinema mode": `enable(output|null)` keeps one output lit and covers every other output in black (null = the output of the focused window, else under the pointer, picked once at request time), `set_glow(0..100)` adds an optional glow on the dark outputs made from the colors along the lit output's border. Like the display filter it needs no permission and lives only as long as the requesting object (latest request wins as a whole; `CinemaModeState::current` is polled per output per frame and fades the level over 600 ms). A lit output that no longer exists means the mode does nothing instead of blacking out everything. Rendering: dark outputs get a `Cover` (opaque black quad, or a ~12 logical px/texel CPU-rasterized glow image scaled up by the GPU - nearest point on the lit rect's border, color from that border position, quadratic falloff) pushed *behind* the cursor/overlays in `custom_elements` and skipped while the screen is locked. The lit output is sampled by the **udev** backend only (winit has a single output, so cinema mode is a no-op there): ~8 Hz while a glow is on, `sample_udev_border` re-composites the frame into an offscreen buffer like `capture_udev_frame` and reads four thin edge strips (`cinema::read_border_strips`; the readback of that offscreen buffer is already top-first: `GlesMapping::flipped()` is a hard-coded `true` that must *not* be honoured, or the glow comes out mirrored), `CinemaRender::submit` smooths them into per-side color rows. Glow raster/geometry/fade logic is unit-tested; the GPU readback and the udev render path are not testable without a real DRM session.

### Standard protocol integrations that bridge to the shell

- `src/protocols/ext_workspace.rs` — server side of `ext-workspace-v1`; a thin read/write projection of `shell::workspace` state, not a second source of truth. `sync()` is the entry point.
- `src/protocols/foreign_toplevel.rs` — server side of `wlr-foreign-toplevel-management-unstable-v1`; reads window lists from `shell::workspace::all_windows` (deliberately not `state.space.elements()`, which would drop windows on inactive workspaces). `sync()` is the entry point.

These three `sync`/`fire`/`check` entry points (`ext_workspace`, `foreign_toplevel`, `workspace_windows`) intentionally don't diff against previous state before emitting — call all three together after any window/workspace-affecting event, matching the existing call sites.

### Companion binaries (`src/bin/`, not part of the compositor process)

- `ironland-workspaces` — a standalone Wayland client bridging `ext-workspace-v1` (+ best-effort `ironland-workspace-windows-v1`) to line-delimited JSON on stdin/stdout, since Quickshell has no built-in `ext-workspace-v1` support. See its module doc for the exact wire format.
- `ironland-portal-global-shortcuts` — the `org.freedesktop.impl.portal.GlobalShortcuts` xdg-desktop-portal backend, D-Bus-activated, bridging portal `BindShortcuts` requests to `ironland-shortcuts-v1`'s `bind` request. Packaging note: `resources/ironland.portal` is checked in as-is; the matching `.service` file's `Exec=` is generated by `flake.nix` (needs the Nix output path), not checked in.
- `ironland-portal-screenshot` / `ironland-portal-screencast` — the `Screenshot` and `ScreenCast` xdg-desktop-portal backends. Both capture over the compositor's privileged capture socket (`$IRONLAND_CAPTURE_SOCKET`) via `ext-image-copy-capture-v1` (`src/protocols/screencopy.rs` is the compositor side and gates every capturer by executable). `ironland-portal-screencast` publishes frames as a PipeWire video node (the `pipewire` crate needs libpipewire + libclang at build time, see `flake.nix`'s `bindgenEnv`); `xdg-desktop-portal` itself opens the PipeWire remote, so there's no `OpenPipeWireRemote`. Like the shortcuts backend, each has a checked-in `resources/*.portal` and a flake-generated `.service`.

### Nix packaging (`flake.nix`, `nix/module.nix`)

- `packages.default` builds the compositor via crane, wraps `Xwayland` onto `PATH` (Smithay's `XWayland::spawn` looks it up by bare name), and installs the portal registration files described above.
- `packages.settings-gui` builds the Go GUI via `buildGoModule`, tagged `wayland` so Fyne's glfw backend doesn't require `DISPLAY`.
- A VM configuration (`nixosConfigurations.compositor-vm`) autostarts the compositor as user `dev`, driven by `scripts/run-vm`.
